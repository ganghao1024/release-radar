# GitHub Actions 与 GitHub Pages 部署

## 运行链路

```text
main 推送 / 手动运行 / 每小时 :17 UTC
  → 安装 Python 依赖
  → 恢复上次数据缓存
  → 运行解析、分类、去重和日期测试
  → 采集官方 RSS / Atom / HTML
  → 保留最近 180 天记录、生成来源健康状态
  → 生成静态网页、Markdown、RSS
  → 保存缓存与审计 artifact
  → GitHub Pages 部署
```

工作流：`.github/workflows/publish.yml`。每小时第 17 分钟是计划时间，不是准时保证；GitHub 可能排队延迟，长期不活跃的公开仓库也可能暂停定时任务。页面超过 3 小时未更新会提示检查 Actions。

## 首次部署

1. 把本项目推送到 GitHub 仓库的 `main` 分支。
2. 在 `config/site.json` 设置 `repository` 为仓库公开 URL、`url` 为实际 Pages URL（包含仓库子路径和尾随 `/`）。
3. 仓库 Settings → Pages → Source 选择 **GitHub Actions**。
4. 仓库 Actions 中启用并运行 **Collect and publish Release Radar**。
5. 等待 `build` 和 `deploy` 成功，打开 deployment 输出的地址。
6. 验证网页、`data/latest.json`、`feed.xml`、两个 Markdown 下载链接可访问。

公开仓库通常可使用 GitHub Free 的 Pages。私有仓库是否可用取决于账户计划。此方案不创建付费资源、不需要自定义域名、不需要云服务器。

## 权限

- build 仅 `contents: read`。
- deploy 仅 `pages: write` 与 `id-token: write`，通过 GitHub OIDC 发布。
- 不在仓库存储个人 token。无需自行设置 Secrets。
- 不将采集结果自动提交 main，避免每小时制造提交和触发循环。
- 新建 pull request 只测试构建，不发布，也不运行不可信代码的写权限任务。

## 数据保留与故障

- `.cache/state.json` 由 Actions cache 在运行间恢复；缓存有容量和过期限制，不是永久数据库。
- 缓存缺失时回退到仓库 `data/latest.json` 的真实快照，再拉取当前内容；不保证恢复源订阅窗口之外的中间历史。需要永久归档时应增加持久对象存储。
- 本次部分来源失败：保留历史条目，并在来源页显示失败。
- 本次全部来源失败：采集步骤失败，阻止发布，上次线上网页保留。通过 GitHub Actions 自身失败通知检查。
- 日期缺失：保留 `published_at: null`，仅在“全部归档”显示；`first_seen_at` 只表示首次发现，不冒充发布日期。
- URL 标准化去除追踪参数并合并同一链接的多源记录。同厂商、同地区、同日、同阶段且标题完全相同的记录可合并，保留全部原始链接。不同标题不做跨语言语义合并。
- 每个 HTML 来源最多读取 16 个文章详情，避免无界抓取；内容超过 8MB 拒收；超时自动重试一次。

## 维护

```sh
# 定位一个来源
python scripts/collect.py --only samsung
# 重新生成页面与 Markdown
python scripts/build.py
# 回归检查
python -m unittest discover -s tests -v
```

`--only` 是局部诊断；最终发布前运行完整采集，以统一检查全部来源。官网返回 HTML 而非 RSS、选择器失效、日期结构改变时，应修复适配器；不能把 HTTP 200 当成验收。

线上来源清单随每次部署更新；仓库中的清单反映提交时状态。Actions 的 `source-audit` artifact 保存同次文档与数据，保留 30 天。

## 页面与安全

所有本地资源均用相对路径，可在 `/<repo>/` 下运行。外部字体加载失败时使用系统中文字体。页面通过文本转义显示采集内容，只允许 HTTP/HTTPS 原文链接，不执行文章中的 HTML 或脚本。

源码只含公开来源和公开资讯；账号令牌、登录态与个人文件不进入站点输出。构建目录只复制网页、公开数据和文档。
